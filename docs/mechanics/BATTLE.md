# Battle timeline contract

The neutral M3 scheduler, command, damage and RNG baseline below is owner-approved. D04–D17 now also fix the structural effect, type-component, mix, capture, progression, world and persistence rules; exact engine balance tables explicitly deferred in the decision register remain implementation artifacts. Fixed throughout: discrete deterministic timeline, independent move timing/cooldowns, and no animation/frame authority.

## Clock and scheduler

Use nonnegative integer logical ticks with checked addition, initially specified mathematically and later refined to a compiler-supported bounded representation. The approved scale is 60 logical ticks per presentation second. Rendering maps ticks to visual time without feeding frame deltas into rules; the event-driven scheduler jumps between deadlines rather than stepping 60 times per second. Exhaustion returns a deterministic terminal diagnostic; never wrap to zero.

The active logical battle clock is capped at 216000 ticks (one hour); paused input time does not count. Windup is 0–600 ticks, recovery 30–600 ticks and ordinary cooldown 60–3600 ticks. Any project value outside these bounds rejects. Scheduling or advancing beyond the clock cap returns core `Timeout`, discards pending events and never wraps; single-player campaign policy treats Timeout as player loss while replay history retains Timeout.

Proposed phase machine: Ready → Windup → Execute (atomic ordered effects) → Recovery → Ready. Windup may be zero: current-tick execution is enqueued only after the complete command batch commits, follows the normal event key and cannot reopen same-tick input. Readiness requires alive/active and recovery finished; each move also requires its own cooldown finished. Recovery and cooldown are independent. Every executed action imposes at least 30 ticks of actor-wide recovery; content may specify a longer bounded value. One actor has at most one reserved action.

Approved event-key prefix: `(dueTick ascending, phaseRank ascending, priority descending, acceptedSpeed descending, actorId ascending, actionSequence ascending, eventOrdinal ascending)`. `acceptedSpeed` is captured from the actor when the command is accepted and stored in the execution event; later speed changes do not reorder it. Proposed queued phase ranks: expiry/readiness, execution. Same-action aftermath belongs inside the execution transaction. Check completion immediately after that transaction and before the next event; on a terminal result commit once and discard all pending events without charging actions that never reached execution. If the completed action leaves every side without a viable combatant, the core result is Draw. Single-player campaign policy treats Draw as player loss while the battle record and replay retain Draw. Boundary semantics use `now >= deadline`; expiration happens before execution at the same tick. Stable IDs are allocated before battle and remain stable. Never use insertion order from a hash map or thread completion order.

At each step drain already-due deterministic events in total order, evaluate completion at the approved boundary, then surface ready command opportunities. When required commands are missing, return AwaitingCommands with unchanged time. Validate the complete submitted batch against that unchanged barrier snapshot and commit all commands in stable actor order only when every command is valid. A rejected batch changes no simulation state or RNG. When no commands are missing, advance to the next due event. If no event exists, first return any applicable completion result, otherwise surface Ready command opportunities; if a nonterminal state has neither events nor command opportunities, return a deterministic SchedulerStalled diagnostic without advancing time. This is an invariant failure to test, not an implicit victory. No automatic repeated action is scheduled at the same tick: zero-windup actions enqueue an execution event at the current tick only after the entire command batch has been validated and its reservations committed. Drain these events by the same total event key, not command-arrival or batch-commit order; they cannot reopen a same-tick input opportunity. Every executed action has at least 30 ticks of recovery. Per-step fuel bounds implementation work; fuel exhaustion yields a resumable internal cursor, not a partial externally visible action.

## Recommended selection policy (D01)

Pause logical time for a command barrier covering all currently ready controllable actors. Collect one legal command or explicit Wait per actor; AI observes the same pre-command snapshot and chooses deterministically. Validate and commit the batch in stable actor order; reject conflicting or stale commands with typed diagnostics. Reserve/commit the valid batch atomically without executing effects during the commit loop; an invalid or mutually conflicting batch returns diagnostics and leaves simulation state/RNG unchanged for correction against the unchanged barrier snapshot; never let replacement input observe partially committed actions. Once committed, execute due actions in event-key order. Future networking would record the accepted batch order. This supports accessibility and reproducible local play. Continuous time adds input latency policy and real-time pressure; slowed time needs another clock. Neither is silently assumed.

The Wait command moves a Ready actor into a wait/recovery phase until `now + WAIT_TICKS`. At new-game creation the player must select 30, 60 or 120 ticks for the entire game, producing respectively a more action-like, balanced or more turn-like command cadence. The choice is immutable within that game and belongs in save and replay identity. Projects cannot override the three engine-owned choices. Wait consumes no move cooldown and creates a scheduled readiness event. A waiting actor is excluded from barriers until that event; an actor with every move cooling can always choose Wait if the clock addition is representable. This prevents a zero-time loop of immediately reopening the same barrier. WAIT_TICKS does not rescale other battle durations.

## Acceptance and execution

Proposed acceptance preconditions: battle active; actor alive/active/Ready; target legal; source moves known; move/recipe allowed and learned; every source off cooldown; resources sufficient; timestamps representable. Reserve the actor and all sources atomically. An invalid command consumes no RNG, time, items or source cooldown.

Ordinary creator-authored move cooldowns are 60–3600 ticks. Acceptance reserves the selected move, but its cooldown begins only when the action reaches execution and attempts to use it. Reservations prevent reuse during windup. If the actor becomes unable to act before execution, cancel the action, release its reservation and do not start cooldown; voluntary cancellation is unavailable. An invalid-target execution fizzle pays full cooldown and normal recovery. Cooldown deadlines are monotonically extended rather than shortened. A mixed execution charges each source `ceil(3 × ordinaryCooldown / 2)` at attempted execution, with a mixed ceiling of 5400 ticks. Pre-execution actor cancellation is free; invalid-target mixed fizzle charges both sources. Execution must check all deadline arithmetic before committing either cooldown or any effect so overflow cannot produce a partial action.

Target identity is locked at acceptance. Acceptance also snapshots the attacker's offensive inputs for the selected move, including relevant attacker stages, bonuses and committed move parameters. Effective Attack, Defense, Special Attack, Special Defense and Speed are always integers in 1–9999 after modifiers. At execution revalidate actor and target state; never retarget automatically. A now-invalid locked target produces a deterministic fizzle, starts full move cooldown, applies normal recovery and consumes no hit, critical or damage RNG. For a valid target, read current target defenses and target-side modifiers, then compute checked integer base damage as `floor(movePower × (2 × attackerLevel + 50) × capturedAttack ÷ (300 × currentDefense))`, with move power 1–200, positive defense and one floor after the complete ratio. Nondamaging moves have no damage-power value. There is no minimum damage: a successful nonimmune result may be zero. Emit `NoDamage` distinctly from `Miss`, `Immune` and `Fizzle`; after observation the UI marks the move as currently unable to damage that target and recomputes that knowledge when relevant state changes. Commit exact damage atomically at the scheduled execution tick. Pure previews may report possible outcome ranges from the offensive snapshot, visible defense and known queued deterministic changes, but consume no RNG, change no state and are not authoritative. Host calculation time never advances logical time or adds damage delay. Resolve declared effects in author order inside one atomic action; named statuses have one instance, refresh duration and retain the stronger magnitude, subject to engine protection, immunity and incompatibility tables. A KO blocks later actors' pending actions, and battle completion is checked after the action transaction. Exact progression, capture and type-chart balance tables follow their approved structures in D11–D12/D15.

All random chances use integer units in 0–10000, where one unit is 0.01 percentage points. A random check samples an unbiased integer in `[0,10000)` and succeeds iff the sample is less than its chance. Canonical state and replay data never use floating-point probabilities. Ordinary move base accuracy is 500–10000. Accuracy and Evasion stages are each bounded to −6…+6; clamp captured attacker Accuracy minus current target Evasion to net stage `n` in that range. Multiply by `(3+n)/3` for nonnegative n or `3/(3+abs(n))` for negative n, using exact integer arithmetic and one floor, then clamp an ordinary legal chance to 500–10000. An explicit schema-permitted always-hit property bypasses the ordinary accuracy formula and hit draw; ordinary 10000 accuracy does not. After a damaging action passes accuracy, its baseline critical chance is 625/10000 (6.25%) before engine-owned modifiers and ordinary total critical chance clamps to 2500/10000 (25%). Nondamaging actions do not check critical. A critical respects all attacker and target offensive/defensive stages and multiplies corresponding resolved normal damage by exactly 2; zero remains zero. Cancellation/fizzle consume no samples; ordinary valid-target attempts consume accuracy; misses stop; deterministic block/immunity and nondamaging hits consume no critical; successful nonimmune damaging hits consume critical even if final damage is zero. One reducer-owned xoshiro state samples in event order; bounded sampling has a 64-candidate budget and atomic `RngSamplingExhausted` failure. Multi-type power uses the approved 1–4-component canonical quotient/remainder allocation, and exact `3/2` STAB applies once to each matching component before the component's approved floor and checked aggregate sum.

## Test obligations

Golden traces must cover equal-tick KOs, priority ties, expiry boundaries, input arrival permutations, zero-windup moves, positive recovery, cooldown expiry during windup, target invalidation, clock exhaustion, source reservations, all-moves-cooling Wait, all-Wait batches, empty-queue stalls, batch rejection/correction against the same snapshot, zero-windup priority ordering, immediate completion versus pending same-tick actions, rejection with unchanged RNG and termination. The same accepted log under 30 FPS, 60 FPS and headless projection must have identical state/event hashes. Determinism is not a promise of fairness; tie semantics need explicit review.
